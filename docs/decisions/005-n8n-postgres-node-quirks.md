# 005: Real n8n node quirks found by actually running workflows

`docs/decisions/003-n8n-workflow-strategy.md` explained why workflow JSON was spec-first and unverified for most of this project — no live n8n instance was available. Once a real Telegram bot token made it worth standing up n8n via its REST API (headless, no browser — owner-account bootstrap + session cookie + `/rest/workflows`), `health_check` became the first workflow actually built and executed for real. Two non-obvious bugs surfaced that silently produce wrong behavior with **no error at all**, which no amount of spec review would have caught. Apply both rules to every other workflow before assuming it works.

## Quirk 1: a node fed zero input items simply doesn't run — no error, no output

`health_check`'s "Previous check result" query (`SELECT ... LIMIT 1`) returns 0 rows on the very first run (empty table). A Postgres node with 0 matching rows emits **0 output items**, not one item with null/empty data. Every downstream node — `Compare to previous`, `Insert workflow_logs row`, the `IF`, the Telegram send — then received 0 input items and **did not execute at all**. The overall execution still reported `status: "success"` and `finished: true`, because nothing actually errored; the workflow just quietly stopped partway through.

This silently breaks any workflow pattern that does "look up whether X already exists, then branch" when X might legitimately not exist yet — which is most of this project's dedup/anti-duplicate-send patterns (`deliveries` reservation checks, `deduplicate_posts`' similarity lookup, `news_sources` existence checks, etc.).

**Fix**: set `"alwaysOutputData": true` on any node whose query might return zero rows but whose output is still needed downstream (a sibling property to `continueOnFail`, at the node's top level, not inside `parameters`). Confirmed live: without it, the workflow silently truncated; with it, `Previous check result` emitted one item with `{}` and everything downstream ran correctly.

## Quirk 2: the Postgres node's "Query Parameters" field breaks past ~6 comma-joined expressions

The `executeQuery` operation's `options.queryReplacement` field is documented as "a comma-separated list of the values you want to use as query parameters," intended to be filled with multiple `={{ expr1 }},={{ expr2 }},...` blocks. Empirically, this reliably worked with 6 parameters built this way and silently dropped the 7th (`Variable $7 out of range. Parameters array length: 6` — the query itself referenced `$7`, but only 6 params ever got bound). A separate, earlier symptom of the same underlying fragility: a single parameter whose _resolved value_ itself contained commas (a `JSON.stringify()`'d object) produced `invalid input syntax for type json` / `"The input string ended unexpectedly"` — the value was getting truncated at an internal comma.

**Fix**: instead of comma-joining multiple `={{ }}` blocks, set `queryReplacement` to **one single expression that evaluates to a real JS array**:

```
={{ [ value1, value2, value3, value4, value5, value6, value7 ] }}
```

Confirmed live with 7 parameters (mixing strings, booleans, and a number) — every value bound correctly, `$1` through `$7`. This form appears to bypass whatever string-splitting logic breaks the comma-joined form, and it should generalize past 7 too (untested above 7, but the mechanism — n8n keeping a single-expression field's native return type instead of stringifying it — doesn't have an obvious reason to cap out).

Also: never pass a multi-key JSON blob as a single text parameter cast to `::jsonb`. Build it in SQL instead via `jsonb_build_object('key1', $1::type, 'key2', $2::type, ...)` from individual scalar parameters — sidesteps the comma-in-value problem entirely and is what `health_check`'s `Insert workflow_logs row` node actually does.

## Quirk 3: `IF` node `exists`/`notExists` operators enforce strict typing on the value itself

Found while building `add_source`. Two variants of the same underlying issue:

- Checking whether a `continueOnFail` HTTP node errored via `{ leftValue: "={{ $json.error }}", operator: { type: "string", operation: "notExists" } }` throws `Wrong type: ... is an object but was expecting a string` — a node's `error` field is a whole error object, not a string, and the `string`-typed operator validates against that regardless of the operation being an existence check.
- Comparing a genuinely numeric `id` field (from a Postgres `SELECT`) the same way, with a `string`/`notEmpty` operator, throws `Wrong type: '4' is a number but was expecting a string`.

**Fix**: don't use `exists`/`notExists`/`notEmpty` operators against fields of unpredictable or non-string type. Use a plain boolean expression instead: `{ leftValue: "={{ $json.error === undefined }}", rightValue: true, operator: { type: "boolean", operation: "equals" } }`. This sidesteps type inference entirely — the expression itself resolves to a boolean before the condition ever runs.

## Quirk 4: the HTTP Request node's output replaces `$json` entirely — original item fields are gone

Found while building `poll_rss_sources`. A node chain like `Postgres (SELECT sources) -> HTTP Request (fetch each source's feed) -> Code (needs the source's id)` looks like it should just work via n8n's automatic per-item iteration — but the HTTP Request node's output _replaces_ the item's `$json` with the response (e.g. `{ data: "<xml>..." }`); it does **not** merge in the original input item's other fields (`id`, `rss_url`, ...). Referencing `$json.id` after an HTTP node silently returns `undefined` — no error, and since `JSON.stringify` drops `undefined`-valued keys, the field doesn't even show up as `null` in the output, making this easy to miss when just eyeballing an item.

**Fix**: reference the original data via `$('NodeName').item.json.field` (pairedItem-based lookup — n8n tracks which output item came from which input item through the chain) in any node running in per-item mode. In a `Code` node set to **Run Once for All Items** (which breaks the 1:1 pairing `.item` relies on), use `$('NodeName').all()` and zip it against `$input.all()` by array index instead — valid as long as every node in between preserves item order and count 1:1, which simple auto-iterating nodes do.

## Quirk 5: `continueOnFail` puts the error in different places on different node types

Found while building `send_instant_alerts`, sending to a deliberately-invalid Telegram `chat_id` to test the failure path. On the HTTP Request node (Quirk 4's context), `continueOnFail: true` nests the error _inside_ `$json.error`. On the **Telegram node**, it does not — the item comes back as `{ json: {}, error: "Bad request - please check your parameters" }`, with `error` as a **sibling of `json`, not a property inside it**. An `IF` condition checking `$json.error === undefined` therefore always sees `undefined` and incorrectly takes the success branch, even though Telegram genuinely rejected the request (confirmed independently via a direct `curl` to Telegram's API: `400 - "Bad Request: chat not found"`). This is silent — the workflow reports `"success"`, and (in this project's case) would have marked a delivery as sent, and released nothing, when the message never actually arrived.

**Fix**: don't rely on `continueOnFail` + field-inspection for nodes whose error shape isn't already confirmed (each node type's implementation decides this independently). Use n8n's structural error branching instead: remove `continueOnFail`, set `"onError": "continueErrorOutput"` on the node, and wire **two separate output connections** — index `0` for success, index `1` for the error case. This sidesteps the question of where any given node type puts its error entirely, since success/failure is now which _output_ fired, not a field to inspect.

## Quirk 6: n8n's expression parser can choke on a large inline object literal, reporting "invalid syntax" — not an HTTP error

Found while building `classify_with_claude`. An `={{ }}` expression embedding a sizeable literal object directly — in this case, `JSON.stringify({ ..., tools: [<the classification tool's full JSON schema, ~15 fields>], ... })` written inline — failed at **parameter-resolution time**, before any HTTP request was even attempted: `Error: invalid syntax` from `Expression.renderExpression`, not from the HTTP call. Deceptive to debug: with `onError: continueErrorOutput` in place, this is easy to mistake for a routed API failure (a 401, a network error) rather than n8n rejecting the expression's own source text — the node's `executionStatus` reports `"error"` either way, and only reading the actual `error.message` (`"invalid syntax"`, referencing `Expression.js`) versus an HTTP client error (`AxiosError`, a real status code) distinguishes the two.

**Fix**: don't embed large literal objects directly inside a `={{ }}` expression. Build the value in a preceding **Code** node instead (a full JS object literal is unambiguous there — n8n's own expression parser never has to tokenize it) and have the consuming node reference the simple output, e.g. `={{ $json.body }}`. Confirmed live: identical payload content, moved into a Code node's `return { json: { body: JSON.stringify(requestBody) } }` and referenced as `jsonBody: "={{ $json.body }}"`, resolved and sent correctly — the real request reached Anthropic's API and got a genuine `401 authentication_error`, not a parser error.

## Quirk 7: trigger nodes created via raw API POST get no `webhookId` — activation registers a broken URL with the external service

Found while going fully live on `telegram_commands` — the first workflow in this project using a real webhook-based trigger (`n8n-nodes-base.telegramTrigger`) rather than a schedule/manual/Execute-Workflow trigger. Building it via `POST /rest/workflows` (exactly like every other workflow so far) and activating it via `PATCH .../active: true` did call Telegram's `setWebhook` — but with a malformed URL (`/webhook/<workflowId>/<node name, url-encoded space and all>/webhook`) that doesn't match any route n8n actually serves, so every real incoming message got `404 Not Found` and queued undelivered on Telegram's side (`pending_update_count` climbing, `last_error_message` visible via `getWebhookInfo`). The node's own JSON had `"webhookId": null` — normally auto-assigned as a UUID when a trigger node is added through the editor UI, this never happened via the raw API path.

**Fix**: manually assign a UUID to the trigger node's `webhookId` field before activating (`node['webhookId'] = str(uuid.uuid4())`), then deactivate and reactivate. Confirmed live: `getWebhookInfo` then showed the correct URL shape (`/webhook/<uuid>/webhook`), `pending_update_count` dropped to 0, and real messages started reaching the workflow (`mode: "webhook"` executions, not `"manual"`).

**Consequence for `docs/workflows/telegram_commands.md`'s exported JSON**: the checked-in `n8n/workflows/telegram_commands.json` has its `webhookId` deliberately replaced with a placeholder rather than the dev instance's real UUID — importing it fresh and activating through the n8n UI (not raw API) will get a properly auto-assigned one, sidestepping this whole issue for anyone following the normal import path. This quirk is specific to the build methodology used in this project (headless API automation), not to n8n's normal UI-driven usage.

## Quirk 8: Telegram Trigger v1.1's secret-token check can crash the entire n8n process, not just one request

Found _after_ Quirk 7's fix — real messages were being received (webhook 200s, executions succeeded), but the user reported the bot as unreliable ("doesnt work"). n8n's own container logs showed `Error: Input buffers must have the same byte length` with no stack trace, and the container's uptime had reset (Docker's `unless-stopped` policy silently restarting a crashed process). Root cause, found in `TelegramTrigger.node.js`: the Telegram Trigger node's `typeVersion 1.1` verifies an `X-Telegram-Bot-Api-Secret-Token` header against an internally-expected secret via `crypto.timingSafeEqual(secretBuffer, headerSecretBuffer)`. `timingSafeEqual` **throws** `RangeError: Input buffers must have the same byte length` when the two buffers differ in length — it does not return `false`. Since this webhook was registered manually (Quirk 7's fix path bypasses n8n's normal activation flow, which would call Telegram's `setWebhook` _with_ a matching `secret_token`), Telegram was never given a secret to echo back — the header arrives empty, `Buffer.from('')` is 0 bytes, the expected secret is N bytes, lengths mismatch, and the **uncaught** `RangeError` takes down the entire n8n process on every single real incoming message, not just that request. This is far worse than a per-request bug: it's an outage that repeats on every message until fixed, each one costing a ~15-20s restart during which the bot is fully down.

**Fix**: set the node's `typeVersion` to `1` instead of `1.1` (the check is explicitly gated behind `if (nodeVersion > 1)` in the node's source) — this skips secret-token verification entirely. Confirmed live: a synthetic Telegram-shaped update posted directly to the webhook URL after this change returned `200`, the execution succeeded, and — critically — the n8n container's uptime/logs showed no new crash, where the same class of request had crashed it before. The trade-off is losing secret-token verification (a defense against something else forging requests to your public webhook URL); acceptable for a personal dev setup behind an unguessable ngrok UUID path, worth reconsidering for any real production deployment (where the proper fix is registering the webhook through n8n's actual activation flow, not raw API calls, so the secret gets set correctly in the first place).

## Quirk 9: Telegram Send Message defaults to Markdown parsing, silently eating literal underscores

Found from real user feedback — the `/help` reply's `/add_source` came through to the user as `/addsource` (no underscore), so they reasonably tried that and got "unknown command." The Telegram node's `sendMessage` action, with no `parse_mode` set explicitly, parses the message body for Markdown-style formatting by default; a bare underscore is Markdown's italic delimiter, so `/add_source` gets read as `/add` + start-of-italic + `source` — the underscore itself is consumed as a formatting character and never rendered. Confirmed via the message's returned `entities` array containing `italic`-type spans at exactly that position. This silently corrupts **any** literal underscore in a message — command names being the obvious case here, but the same applies to underscores in URLs, code, usernames, anything.

**Fix**: set `additionalFields.parse_mode: "HTML"` explicitly on every Telegram send node (HTML mode doesn't treat underscores as special), and audit message text for characters HTML mode _does_ treat specially — `<`, `>`, `&`. This project's help text used a `<placeholder>` convention for `/add_source <url>`, which under HTML mode reads as an (invalid, unrecognized) HTML tag and would likely have been stripped or rejected by Telegram's parser; changed to `«placeholder»` instead. Also disabled `additionalFields.appendAttribution` (n8n's own "sent automatically with n8n" footer, which uses Markdown-link syntax for its own text) purely for cleaner output, not because it caused a problem itself.

## Quirk 10: aggregating items breaks `pairedItem` lookups downstream — `$('Node').item` throws, not just returns `undefined`

Found from another real user bug report: `/sources` errored while `/help` and `/add_source` worked fine through the exact same final nodes. The difference: `/sources`' path runs `List sources` (a Postgres query, N rows) through `Format sources list` (a **Run Once for All Items** Code node that combines N items into 1 summary message) before reaching `Prepare reply`, which does `$('Parse command').item.json.chatId` — a **pairedItem** lookup (`.item`, not `.first()`). Aggregating N items into a new, unrelated item doesn't preserve the pairedItem chain back to the original trigger by default, so n8n can't resolve which upstream item the new one corresponds to. Unlike Quirk 4 (a broken lookup silently returns `undefined`), this is a **hard failure**: `ExpressionError: Can't get data` / `createMissingPairedItemError`, visible in the execution's `error_handler`-eligible failure output — the whole execution errors out, no reply gets sent at all.

**Fix**: when a value is known to be single/constant for the whole execution (here, `chatId` — one incoming Telegram message means exactly one chat regardless of which command branch ran or whether that branch aggregated items), use `$('NodeName').first().json.field` instead of `.item.json.field`. `.first()` just takes the first item unconditionally — no pairedItem resolution required, so it can't throw this way. Reserve `.item` (pairedItem-based) for cases where the correspondence genuinely matters and hasn't been broken by an aggregation step in between.

## Quirk 11: `pairedItem` lookups can become ambiguous crossing an `alwaysOutputData` node in a large batch — even a single, otherwise-safe hop

Found building `classify_heuristic` (a rule-based stand-in for `classify_with_claude`, built with no Claude key available — see `docs/workflows/classify_heuristic.md`). Processing a batch of 50 posts, a `Code` node one hop downstream of a `Postgres` node with `alwaysOutputData: true` (Quirk 1's fix, needed here because a dedup-check query legitimately returns 0 rows for most posts) did `$('EarlierNode').item.json...` and threw `ExpressionError: Invalid expression` / `paired_item_multiple_matches` — `"Multiple matching items for expression"`. This is a _third_ distinct pairedItem failure mode, different from both Quirk 4 (silently `undefined`) and Quirk 10 (aggregation breaks the chain, hard failure): here the lookup was a single hop, immediately after the problem node, with no aggregation anywhere in the chain — exactly the shape that worked fine elsewhere in this same project (e.g. `poll_rss_sources`' "Merge normalized fields"). The only difference was `alwaysOutputData: true` plus a batch of ~50 items, suggesting the synthetic "always output" item n8n creates for a 0-row match doesn't get tagged with an unambiguous item index when many items are processed together — speculative, since n8n's own source wasn't traced this far, but consistent with every case where the failure did and didn't occur across this project.

**Fix**: don't route data across an `alwaysOutputData` node via `pairedItem` at all, regardless of hop count. Instead make that node's own query **self-contained** — have it `SELECT` back every field anything downstream needs as literal passthrough columns (e.g. `$1::text AS title, $2::text AS summary, ..., (SELECT ... ) AS matched_id`) alongside whatever it's actually computing, so the node's own output already carries full context forward through plain `$json` access. Confirmed live: rewriting the dedup-check query this way, re-running against the same 50-item batch that previously failed, completed with zero pairedItem errors.

## Consequence for the other workflow specs

Every remaining spec needs: the array-expression form for `queryReplacement` on any insert/update with more than a couple of dynamic values (`posts`, `news_items`, `sources`, `deliveries`, ...); `alwaysOutputData: true` on any "does X already exist?" lookup that might return zero rows when something downstream depends on getting an item regardless; boolean-expression conditions (not `exists`/`notExists`/`notEmpty` operators) on any `IF` node checking a field whose type isn't guaranteed to be a plain string; pairedItem-based lookups (`$('NodeName').item.json...`) for any field needed after an HTTP Request node that isn't part of that node's own response; and `onError: continueErrorOutput` with two wired outputs — never `continueOnFail` + field-checking — for any node (Telegram, or any other integration node not yet confirmed) whose failure path matters. None of these ten are visible from reading the spec Markdown alone — all ten were found only by executing a real workflow against real Postgres/HTTP/Telegram responses and checking actual results, not by trusting an execution's reported "success" status.

## Not an n8n bug, but worth flagging: Python string-escaping mistake produced literal `\n` in a Telegram message

Found from real user feedback on `/help`'s formatting — this one is on the build tooling, not n8n. The Python script generating `telegram_commands`' node parameters wrote the help text's line breaks as `"\\n"` (an escaped backslash followed by `n`), which is a literal two-character string in Python, not a newline. `json.dumps()` faithfully sent exactly that: a `Set` node value containing five literal `\n` sequences instead of real line breaks, which Telegram rendered as visible backslash-n text. Contrast with `Format sources list`'s `Code` node, which uses `.join('\n')` **inside a string of JavaScript source** — there, `\n` is correctly interpreted by the JS engine at runtime regardless of how the Python source built that JS-source string, which is why `/sources` never had this problem while `/help` did. Fixed by writing the actual newline character into the Python string. Worth remembering for any future workflow built the same way: a `Set`/literal-text field's value is used verbatim, with no code layer to interpret escape sequences — only `Code` node _source text_ gets that second interpretation pass.

## Practical takeaway: build via API + real data, not by hand-authoring blind

`poll_rss_sources` was originally spec'd (Stage E) with nested nested loops (`Split In Batches` over sources, then over feed items) and deferred from having a JSON draft attempted at all, specifically because that shape seemed too complex to hand-author reliably. Once actually building it against live n8n, a simpler design fell out naturally: n8n auto-iterates regular nodes over each input item by default, so no explicit source-level loop was needed at all — only the source→feed-item fan-out (1 input item producing N output items) needed an explicit **Run Once for All Items** Code node. The lesson isn't "the original design was wrong" so much as "the right shape only becomes obvious once you're iterating against real execution data" — which is exactly what building via the REST API against a live instance enables and hand-authored-JSON-with-no-n8n-to-test-against (the situation for most of this project, per `003-n8n-workflow-strategy.md`) does not.
